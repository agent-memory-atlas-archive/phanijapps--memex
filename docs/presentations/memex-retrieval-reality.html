The honest stop

Better is not the same as good enough

Observed hard-MRR gain +0.0216 Required: +0.0500
The candidate did not ship. It improves finding the right page in the top ten, but does not move that page near the top often enough.
  • Production retrieval remains the known SQLite FTS5 baseline.
  • The 100K phase was skipped because no candidate cleared every 10K eligibility gate.
  • The optional rgapi experiment was incomplete at scale and failed closed.

This is the gate doing its job: token savings and recall gains cannot buy permission to weaken ranking quality.

The rational next move

Optimize rank position—not just candidate coverage

Keep

  • The existing accuracy, token, and latency gates.
  • SQLite FTS5 as the portable production baseline.
  • The in-process Python evaluator and isolated-store discipline.
  • The gains already proven in recall, context size, and speed.

Change next

  • Target first-correct-result position directly.
  • Test section-aware evidence and query-intent signals behind the same gate.
  • Reject any approach that only reshuffles ambiguous duplicates.
  • Run 100K only after one candidate clears every 10K gate.
Recommendation: do not relax MRR. Use the new evaluator to develop one stronger deterministic candidate, then promote only the measured winner.

This preserves the priority order: accuracy and token efficiency are co-primary; speed remains a hard constraint.

Bottom line
